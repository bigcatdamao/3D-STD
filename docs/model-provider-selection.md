## 当前发现

3D-STD 当前需要同时面对三类不同用途的模型格式：

- 网页预览和编辑更适合使用 GLB；
- 混元组件生成（自动拆件）当前要求可访问的 FBX 源文件；
- 3D 打印交付仍以 STL 为主要输出格式。

因此，“生成模型、网页预览、自动拆件、打印导出”并不天然共享同一种文件格式。格式转换本身不难，但完整商业化链路还会引入大文件上传、单位校正、临时对象存储、签名 URL、转换任务、失败重试、结果过期和临时文件清理等工程工作。

当前项目还存在以下边界：

- 混元生成资产可以保留供应商任务和 FBX 来源，用于后续组件生成；
- 用户本地导入的 STL/GLB 没有供应商 FBX 来源，不能直接复用当前混元组件生成链路；
- 当前网页导入器主要支持 GLB、glTF、STL 和 OBJ，不把 FBX 作为通用编辑入口；
- Hi3D 自动拆件已经出现多次提交失败和细节损失，不应作为无提示的自动降级路径；
- “STL 转 FBX + 临时云存储 + 混元拆件”具有可行性，但不属于当前作品集主线的必要投入。

## 当前产品决策

当前版本不开发通用 STL/GLB/FBX 云端转换中心，也不承诺所有本地导入模型都能自动拆件。

作品集主线收敛为：

1. 已有效果图 → 图生 3D 模型；
2. 模糊想法 → 3D 创作 Agent → 效果图/多视图 → 3D 模型；
3. 混元生成模型 → 自动拆件；
4. 拆件结果确认 → 榫卯与公差设置；
5. 零件检查 → 修复提示/必要修复 → STL 导出。

本地导入暂时只保证现有预览、编辑、手动拆件、检查和导出能力。自动拆件若缺少可用 FBX 来源，应明确说明限制并引导用户使用手动拆件，不能静默切换到失败率较高的供应商。

## 后续模型选型专项需要回答的问题

- 各供应商的图生 3D、文生 3D、多视图生成、组件拆分和连接件能力是否真正开放 API；
- 官网产品能力与公开 API 能力是否一致；
- 输入和输出支持哪些格式，是否保留原始高模、纹理、UV、材质、对象层级和单位；
- 是否支持直接输入 STL/GLB/OBJ/FBX，组件拆分是否强制指定格式；
- 拆件结果是否降低细节、重拓扑、封口，以及是否输出装配关系和连接点；
- 是否支持榫卯类型、尺寸、公差、连接深度与装配验证；
- 单次费用、并发、任务耗时、文件大小、结果 URL 有效期、失败扣费和取消能力；
- 浏览器预览格式、供应商工作格式和最终打印格式应该如何分层；
- 是否值得引入 COS/R2、格式转换服务和临时文件清理任务；
- 针对人物手办、机甲和简单硬表面模型，真实 good case 率如何。

## 恢复条件

满足下列任一条件时再启动格式与供应商专项：

- 当前混元生成 → 组件拆件闭环无法稳定运行；
- 作品集 Demo 已完成，需要准备商业化技术路线；
- 产品确定必须支持用户本地模型自动拆件；
- 市场出现更适合 3D 打印拆件、封口、榫卯或装配的新 API。
